# Git and source recovery

Git is the default safety net for source changes. It is not a substitute for backups of runtime state.

## New projects

If creating a software project and Git is available:
- initialize a local repository unless the user opted out;
- create an appropriate `.gitignore` before secrets/build artifacts appear;
- keep `.env` and credentials ignored;
- provide `.env.example` with names/placeholders only when useful;
- do not create or push a remote unless requested.

## Existing repositories

Before a non-trivial change:
- inspect `git status`;
- distinguish agent-created changes from pre-existing user changes when possible;
- do not overwrite, reset, clean, or stash unrelated work merely for convenience.

If the working tree contains unrelated changes:
- work around them;
- stage/commit only files/hunks belonging to the current task when commits are part of the workflow;
- never assume uncommitted means disposable.

## Checkpoints

Before a broad or risky refactor, ensure the previous state is recoverable.

Preferred methods, from least intrusive to more explicit:
1. existing clean commit/reference;
2. a focused local commit of changes created for the task;
3. a patch/diff artifact when committing is inappropriate;
4. a branch/checkpoint when the workflow already uses branches.

Do not silently commit unrelated user work just to create a checkpoint.

## Dangerous Git operations

Do not use these without a specific justified need and explicit awareness of consequences:
- `git reset --hard`;
- `git clean -fd` / `-fdx`;
- force push;
- rebase/history rewrite on shared branches;
- deleting branches with unmerged work;
- overwriting files with checkout/restore when they contain user edits.

Prefer non-destructive inspection and targeted restoration.

## Secrets

Before commit/push on projects that handle secrets:
- inspect changed files for obvious credentials/tokens/private keys;
- ensure local env files are ignored;
- do not print secret values into chat/logs/test snapshots;
- if a real secret was committed, removing it from the latest file is not sufficient: treat it as exposed and rotate it; history cleanup is a separate task.

## Commit quality

When the workflow calls for commits:
- keep commits coherent enough to revert;
- avoid mixing unrelated refactors with feature/bug changes;
- include migrations/config generated by the change;
- do not auto-commit if the user or environment expects manual review.

## What Git cannot recover

Git normally cannot recover:
- production database contents;
- uploaded files/object storage;
- external SaaS state;
- secrets that were rotated/deleted;
- cloud resources destroyed outside IaC state;
- runtime queues/caches/events.

Load `data-and-backups.md` for those cases.
